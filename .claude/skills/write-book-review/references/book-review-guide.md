## 1. 전개 골격 (책 리뷰형)

1. **도입** — 독자에게 던지는 질문, 혹은 그 책을 집어들 당시의 고민으로 연다.
   - life 예: "이 글을 읽고 계신 여러분은 현재의 삶에 얼마나 만족하고 계신가요?"
   - tech 예: "어떻게 하면 AI 에이전트를 더 잘 활용할 수 있을까 늘 고민을 합니다."
2. **책을 만난 계기** — 언제·어떻게 이 책을 만났는지. 책은 첫 등장 시
   `[「제목: 부제」](알라딘 링크)(출판사, 연도)` 형태로 링크한다. 저자명은 "OOO 님" 또는 "OOO 저자".
3. **표지 이미지 자리** — `{/* TODO: 책 표지 — /images/posts/<slug>/cover.jpg */}` (§6).
4. **`## 책 소개`** — 저자 소개 1~2문장 + 책의 핵심 관점 + 구성(번호 목록, 각 항목 `**파트명** — 한 줄 요약`).
5. **`## 책 리뷰`** (tech형은 `# <책 주제> 주요 내용` 아래 개념별 `##` 도 허용)
   - 파트마다 `### N부. 키워드 -> 질문형 부제` (life) / `## N. 개념 한 줄` (tech).
   - 파트 내부 순서: **요약 → 경험 대입 → 깨달음/결심**.
     - 요약: 저자의 주장을 "~라고 말합니다 / ~을 제시합니다" 로 전한다. 핵심 개념은 **볼드**.
     - 전환: "책 초반부 부터 뼈맞은 기분이었습니다." 처럼 요약에서 자기 이야기로 넘어가는 한 문장.
     - 경험: 브리프 경험 뱅크의 구체 사례(시기·역할·상황)를 1~3문단으로.
     - 깨달음: "~라는 생각에 이르렀습니다", "~라는 점에 공감했습니다".
6. **(tech형 선택) `## 적용해보기`** — 책의 개념을 실제로 적용한 사례. 코드·표·설정 발췌 가능.
7. **`## 끝으로` / `## 마치며`** — 읽은 시기(솔직한 자기고백 허용: "현생을 살아간다는 변명으로..."),
   책의 메시지를 **한 줄로 수렴**("~는 A, B, C 라는 세 축 위에 있다"), 앞으로의 다짐,
   독자에게 되묻는 질문, 추천과 응원으로 닫는다.

## 2. 요약 : 경험 균형

- 리뷰 파트 **하나하나에** 요약 문단과 경험 문단이 모두 있어야 한다.
  요약만 이어지는 파트는 독후감이 아니라 줄거리 정리다 → REDO 대상.
- 예외: 브리프에서 사용자가 "이 파트는 요약만" 으로 명시한 파트. 이때도 짧은 소감 1문장은 둔다.
- 권장 비율: 파트 단위로 요약 40~60%, 경험·사유 40~60%.
- 경험은 책의 개념에 **대입**돼야 한다. 개념과 무관한 에피소드 나열은 균형으로 치지 않는다.

## 3. 출처 규칙 (창작 금지)

| 재료          | 허용 출처                                          | 없으면                                   |
| ------------- | -------------------------------------------------- | ---------------------------------------- |
| `>` 직접 인용 | 브리프의 "인용(원문)" — 사용자 노트/하이라이트     | 인용 블록을 쓰지 않고 간접 화법으로 전달 |
| 책 내용 요약  | 브리프의 "요약 재료" (사용자 노트 기반)            | 해당 파트 생략 또는 `(확인 필요)`        |
| 개인 경험     | 브리프의 "경험 뱅크"                               | 쓰지 않는다. 절대 지어내지 않는다        |
| 서지 정보     | 브리프의 "서지" (WebSearch 로 확인된 값)           | `(확인 필요)` 표시                       |
| 수치·연구     | 요약 재료에 있는 것만 ("여러 연구를 통해" 수준 OK) | 구체 수치를 만들지 않는다                |

- 경험을 **각색**하는 것(문장 다듬기, 순서 재배치)은 허용. **사실 추가**(없는 프로젝트명·기간·결과)는 금지.

## 4. 서식 관례 (코퍼스 관찰)

- 책 제목은 항상 `「」`. 부제 포함 시 `「함께 자라기: 애자일로 가는 길」`.
- 이론·도식은 이미지 + 불릿 해설 (`book-review-growing-together` 의 몰입 이론 그래프 구간).
- tech형은 개념 비교를 **표**로, 저자의 핵심 문장은 `>` 인용으로.
- 파트 헤딩의 화살표 `->` 는 코퍼스 표기 그대로 허용.

## 5. category 판정 규칙

- 프롬프트에 "테크", "tech", "일상", "life" 키워드가 있는지 확인
- 없으면 질문 프롬프트로 tech 인지 life 인지 사용자가 선택하게 유도
- 모호하다면 넘겨 짚지 말고 질문 프롬프트로 사용자의 정확한 의도를 우선할 것

## 6. 메타데이터 규칙

frontmatter 스키마는 `.claude/skills/write-tech-post/references/frontmatter-schema.md` 를 따르되,
이 스킬에서는 **`category: tech | life` 둘 다 허용**한다(§5 로 판정).

- **title** — 콜론·따옴표·`「」` 가 들어가므로 전체를 작은따옴표로 감싼다.
  - life: `'<고민/주제 한 줄>: 책 「제목」(저자)을 읽고'`
  - tech: `'<핵심 메시지> - 책 「제목」(저자) 리뷰'`
- **description**: "OOO 저자의 「제목」을 읽고, ~을 담아보았습니다 / 정리했습니다." 1~2문장.
- **tags**: 3~5개. tech형은 `책 리뷰` 포함. life형은 주제 개념어(`성장`, `협업` 등) 위주.
  브리프의 tags 를 writer 가 임의로 늘리지 않는다.
- **publishedAt**: 오늘 날짜 `'YYYY-MM-DD'` (작은따옴표 필수).
- **featured**: 기본 `false`. 사용자가 원하면 `true`.
- **series**: 쓰지 않는다(단발).
- **이미지**: 생성하지 않는다. 표지는 `{/* TODO: 책 표지 — /images/posts/<slug>/cover.jpg */}`,
  도식은 `{/* TODO: 이미지 — <설명> */}` 주석만. 깨진 `![](...)` 링크 금지.

## 7. 길이와 밀도

| 유형 | 본문 글자 수(`wc -m`, frontmatter 포함) | `##` 헤딩 | 예상 읽기 시간 |
| ---- | --------------------------------------- | --------- | -------------- |
| life | 약 4,500~7,000자                        | 3개 이상  | 약 5~10분      |
| tech | 약 6,000~12,000자                       | 4개 이상  | 약 8~16분      |

- 재료가 부족해 하한을 못 채우면 억지로 늘리지 않는다 — 오케스트레이터가 인터뷰로 재료를 더 받는다.
